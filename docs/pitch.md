# Pitch: Daily Commit

Three minutes. Talk track below matches the beats in [`demo-script.md`](demo-script.md). Numbers come from `python -m engine.simulate --students 300` and the repo; rerun before presenting if the engine changes.

## Talk track

**0:00 Problem (slide 1).**
"Every CS student knows what to study for interviews. Almost nobody practices consistently. Prep is scattered across five sites, done in cram sessions, and it skips the skill interviews increasingly test: reading and debugging code you didn't write. The daily-practice apps that exist serve the same static question bank to everyone, and some of the answers are wrong."

**0:25 Placement (phone).**
"Daily Commit starts with a short placement. Watch the levels: each answer moves not just its topic but related topics in the same track, so a few questions give a realistic starting map instead of ten identical bars."

**0:55 Day 7.**
"Here's what it looks like a week in. Six-day streak. Five minutes a day."

**1:00 Tradeoff question.**
"Two tracks. System design: real tradeoff questions, like picking a caching strategy, finding the bottleneck in a diagram, or ordering the steps of a design. Every answer updates my rating for this topic and the question's own difficulty, like chess ratings for both players."

**1:15 Tap the buggy line.**
"Debugging: tap the line that's wrong. This question was not written by a person. Our pipeline took a working function, injected a realistic bug, ran the tests, and kept it only because the tests failed. So the answer is guaranteed correct."

**1:30 Miss on purpose.**
"Let me get this one wrong."

**1:40 Tomorrow.**
"Tomorrow's lesson already shifted: the topic I just missed moved into focus. The engine picks questions about 150 rating points below your level, which is roughly a 70% chance of success, hard enough to learn from, easy enough to keep the streak alive."

**2:05 Pipeline (terminal).**
"Here's the pipeline live. A small Python function with its test cases. All pass. The mutator changes exactly one line: here, a comparison flipped. Rerun: tests fail, so the bug is real. And out comes the question you just saw, with the failing test output. If the tests had still passed, the bug would have been thrown away. That's how every debugging question is verified."

**2:40 Impact (slides 5-6).**
"Does the engine actually learn? We simulated 300 students with hidden true skill for two weeks. Question difficulties start as a human's guess, off by about 120 rating points, and the engine corrects them to about 50 on its own. Lessons stay winnable, around 60% success, instead of sliding harder over time, which is something the simulation caught and we fixed tonight. Because the debugging bank is generated, it grows with every function we add, and nobody has to hand-check answers. Five minutes a day, matched to you, and never wrong. That's Daily Commit."

## Slides

1. **Problem.** Three icons: scattered (5 sites), cramming (calendar with one red week), missing skill (code with a bug). One line: "Static banks, same questions for everyone, some answers wrong."
2. **Solution.** Phone screenshot of a lesson. "5 minutes a day. Matched to your level. Verified answers."
3. **Adaptive engine.** Diagram: answer, then student rating and question rating update (Elo), then next lesson picks questions near `rating - 150`. Formula in small type: `E = 1 / (1 + 10^((Q - R)/400))`.
4. **Verified bug pipeline.** Four boxes: working function + tests, inject one-line bug, run tests (keep only if they fail), emit question. Small print: "answers never leak: failure text is generated, never a traceback."
5. **Proof it learns.** Two numbers large: question difficulty error **119 to 52**; lesson success **~60% and steady** (was ~49% and sliding before the fix). Source: 300 simulated students, 14 days.
6. **What's next.** More functions in the corpus, predict-the-output questions, spaced review (already in: missed questions come back the next day), school/club leaderboards.

## Judge Q&A prep

| Likely question | Answer |
|---|---|
| Why Elo instead of a fixed difficulty? | Authors guess difficulty badly (off by ~120 points in our simulation). Elo learns it from real answers, and the same update rates the student. One mechanism, both sides. |
| How do you know a generated bug is the right answer? | We only change one line, the original passes all tests, the mutant must fail at least one, and the failure text is generated by our own runner so it can't leak the line. The answer is the line we changed. |
| What if a mutation is equivalent (tests still pass)? | It's discarded. That's the point of running the tests. |
| Is 60% success low? | It's the realized rate with a small question bank; with the bank centered easier the simulation reaches ~65%. Target is ~70%. The selection logic keeps it from sliding as easy questions run out. |
| Why not use an LLM to write questions? | LLM questions can be wrong. Ours are verified by execution (debugging) or curated (system design). An LLM could later propose functions, and the pipeline would still verify them. |
| How does it scale? | Stateless API + SQLite today (one service). Ratings are per (user, topic) rows and question ratings are shared, so the bank gets better calibrated as more students use it. Postgres is a drop-in when needed. |
| What did you build in 24 hours? | Everything shown: app, API, rating engine, lesson selection, placement, streaks, bug pipeline, 50 curated questions, simulation harness, 80+ automated tests including one that runs this exact demo. |
